# 芽芽 2.0 v7：v6 调用链审查

先审查冻结 v6 代码和已核对的真实开发批次，未发起新 API 调用。

1. 浏览器通过同源 /v6 接口选择合成案例、下一轮及指定页；服务器持有会话、已看页、实际待答和最后四条服务回执。Coreading.make_messages 只构造当前原文、已读且紧邻的前页原文，以及带角色的实际对话。Provider 使用固定北京模型、既有参数和协议 B。服务端结构校验后才生成回执，原始响应另存；迟到草稿不会进入历史。
2. dev-v6-09 第 4 轮：实际请求的书页是 p4、p3，不含 p2。历史虽有 p2，但芽芽的旧话只说“两位都在猜”，没有把各自猜的内容分开。草稿将星星同时归给小象和小狐狸；原文支持的说话者只有小狐狸。缺了直接证据；不能仅凭这一轮断定模型如何利用历史。
3. dev-v6-03 第 4 轮：实际请求含 p3 原文（带信出门、确认老树是收件人）和 p2 原文；不含 p4。草稿却称“把信送给了那棵老树”。这不是 p4 泄露的证据，而是模型把收件对象和已完成动作混同。原文与历史无独立事实复核，结构层允许了这条草稿。
4. 当前批次具体失败请求没有未读页原文。v6 在回翻时会保留较晚页的对话，因此回来时可能拿到当前页之后的可见叙述；v7 将原文证据和对话分别做当前进度过滤，不从会话文本抽取书内事实。
5. 51 次真实生成中，6 次 QUESTION_FORMAT；检查是标点启发，不是语义核验。正文问号可能是真提问、重复追问，也可能只是在引用别人的问句。v7 保留明确定义的检查与可复核的误拦/漏检诊断，不用统计把它说成事实核验。
